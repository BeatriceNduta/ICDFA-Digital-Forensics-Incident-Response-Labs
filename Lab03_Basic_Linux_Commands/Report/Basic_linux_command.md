## Overview

This repository contains my work for **Lab 2A**, a practical lab on core Linux command-line skills used in digital forensics. The lab involved building a structured evidence workspace and practising navigation, file handling, metadata inspection, content searching, safe network checks, shell scripting and archiving.

Linux is widely used in forensics because it exposes the filesystem, processes and devices through plain commands that can be scripted, repeated and documented. These skills support later work such as disk imaging, file recovery, log analysis and tool automation.

## Key Findings

### grep evidence (Task 6)

The command below identified the failed login in the activity log:

```bash
grep -n "failed" evidence/activity_log.txt
```

```
3:2026-06-19 10:05 user=admin action=login status=failed ip=192.168.56.15
```

This is suspicious because the failed attempt was on the `admin` account from `192.168.56.15`, a different address from the only successful login (`192.168.56.10`), and an admin password change followed at 10:40 (found with `grep -Ei "delete|password"`).

### Inodes

An inode is a filesystem record that stores a file's metadata (owner, permissions, size, timestamps, data block locations) under a unique inode number. The filename is only a directory entry pointing to it. In forensics, inode data helps build timelines, identify hard links and support recovery of deleted files.

### Absolute vs relative paths

- **Absolute:** `/home/kali/CIP-B101_Lab2A_Beatrice_Nduta/evidence/lab2a_evidence.txt`
- **Relative (from the lab folder):** `evidence/lab2a_evidence.txt`

### PATH

`PATH` is a list of directories the shell searches, in order, for executables typed without a path. This is why `ls` (in `/usr/bin`) works from any folder, and why adding `scripts/` to `PATH` let the custom script run by name from `/tmp`.

### Why localhost testing is safer

The loopback address `127.0.0.1` never leaves the device. Testing it is legal (I own the machine), avoids triggering intrusion alarms, lets me verify results against what I know is running, and can be undone by restoring a VM snapshot.

### zip vs tar.gz

- **ZIP** compresses each file separately and opens easily on Windows, macOS and Linux, so it suits sharing.
- **tar.gz** bundles files first and then compresses the whole stream, preserving Linux permissions and ownership, so it suits Linux evidence packaging.

## The System Summary Script

`scripts/lab2a_sys_summary.sh` writes the following to `outputs/system_summary.txt`:

- Date and time, user, hostname, kernel and current folder
- Disk space (`df -h`) and inode usage (`df -i`)
- A `tree` view of the evidence workspace

### Running the script

```bash
cd ~/CIP-B101_Lab2A_Beatrice_Nduta/scripts
chmod +x lab2a_sys_summary.sh
./lab2a_sys_summary.sh

# Or run it by name from any folder
export PATH=$HOME/CIP-B101_Lab2A_Beatrice_Nduta/scripts:$PATH
cd /tmp
lab2a_sys_summary.sh
```

## Challenges and Lessons Learned

- **"command not found" when running the script from `/tmp`.** `ls -l` showed that `nano` had saved the file as `lab2a_sys_summary.sh.save.1` instead of the real filename. I renamed it, confirmed the name placeholders were replaced, ran `chmod +x`, and retested successfully.
- **"no such file or directory" error.** This came from using a relative path while already inside the lab folder. I fixed it by checking `pwd` and using an absolute path.
- **Lesson:** Save in nano with `Ctrl+O`, `Enter`, `Ctrl+X`, and verify with `ls -l` before running anything.

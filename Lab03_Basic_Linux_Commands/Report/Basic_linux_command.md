## Overview

This lab builds the Linux command-line skills a digital forensics trainee needs to prepare and document an evidence workspace: navigation, file handling, metadata inspection, content searching, safe network checks, shell scripting and archiving. Linux is widely used in forensics because it exposes the filesystem, processes and devices through plain commands that can be scripted, repeated and documented. Every command was run on my own Kali VM, and network tests were limited to `localhost`.

**Operating system and filesystem information**

<img width="1490" height="801" alt="Fig 2  Os and file system" src="https://github.com/user-attachments/assets/9dbefa20-b569-4098-b12d-b1f839a9df38" />


| Directory | Purpose |
| --- | --- |
| `/home` | Personal directories of regular users (on disk) |
| `/etc` | System-wide configuration files, usually plain text (on disk) |
| `/bin` | Essential executables (on modern Kali it is a link to `/usr/bin`) |
| `/proc` | Running processes and kernel state (virtual, generated at runtime) |
| `/sys` | Kernel's structured view of devices, hardware and drivers (virtual) |
| `/dev` | Hardware and pseudo-devices represented as files (virtual) |
| `/tmp` | Temporary files; memory-backed (tmpfs) on this VM, so contents do not persist across reboots |

**Everything is a file:** Linux presents devices, processes and settings through the filesystem, so the same tools (`cat`, `ls`, `grep`) can read them. Examples: `/dev/sda1` (a disk partition) and `/proc/cpuinfo` (processor details generated by the kernel).

## Task 3: Inodes and Disk Information

```bash

stat evidence/lab2a_evidence.txt

df -i
```

**Inode, stat, disk space and inode usage**

<img width="851" height="608" alt="Fig 3, Inodes and Disk info" src="https://github.com/user-attachments/assets/9a522d5d-6140-4b74-a028-2641b1a9c40d" />


| Observation | Value |
| --- | --- |
| Inode number | 786547 |
| File size | 55 bytes |
| Permissions | `-rw-rw-r--` (0664) |
| Hard links | 1 |
| Root filesystem | `/dev/sda1`, 79G total, 22% used |
| Inode usage on `/` | 10% |

An inode is a filesystem record that stores a file's metadata (owner, permissions, size, timestamps and data block locations) under a unique inode number. The filename is only a directory entry that points to it. In forensics, inode data helps build timelines from creation, modification and access times, identify hard-linked files and support recovery of deleted files. `df -i` shows how many inodes are used and free.

## Task 6: Evidence Search with grep

```bash
cat > evidence/activity_log.txt <<'EOF'
2026-06-19 09:10 user=aminu action=login status=success ip=192.168.56.10
2026-06-19 09:25 user=guest action=file_copy status=success file=report.docx
2026-06-19 10:05 user=admin action=login status=failed ip=192.168.56.15
2026-06-19 10:20 user=aminu action=delete status=success file=temp.txt
2026-06-19 10:40 user=admin action=password_change status=success
EOF
grep "login" evidence/activity_log.txt
grep -n "failed" evidence/activity_log.txt
grep -Ei "delete|password" evidence/activity_log.txt
grep -Ei "192\.168\.56\.[0-9]+" evidence/activity_log.txt
```

`PATH` is an environment variable listing the directories the shell searches, in order, for executables typed without a path. ## Challenges and Resolution

- **`command not found` when running the script from `/tmp`.** `ls -l` showed that `nano` had saved my work as `lab2a_sys_summary.sh.save.1` instead of the real filename. I renamed it, confirmed the name placeholders were replaced, ran `chmod +x` and retested successfully.
- **`no such file or directory` error.** This came from using a relative path while already inside the lab folder. I fixed it by checking `pwd` and using an absolute path.
- **Lesson learned:** save in nano with `Ctrl+O`, `Enter`, `Ctrl+X`, and always verify with `ls -l` before running a script.

## Reflection

Command-line skills matter in digital forensics because evidence work must be precise, repeatable and documented. This lab showed how a structured workspace keeps evidence organised, how inode and `stat` data reveal file metadata, how `grep` and `find` narrow large sources down to the relevant lines and files, and how scripts and archives make results reproducible and easy to hand over. Working only on my own VM and on localhost also reinforced that forensic work must stay within authorised systems, and that every result should be verified and explained, not just produced.
